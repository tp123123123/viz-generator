# 用 vibe coding 做前端，以及生成式可视化：相关工作整理

这份材料用于和导师讨论选题前的背景整理。它只覆盖两块：用 vibe coding 做前端的能力基准，以及 2025–2026 年生成式可视化的主要工作。数字都来自对应论文或基准页面，不同任务的通过率不能合成一个总分。

整理时间：2026 年 10 月。ViBench 项目网站上更晚的小规模重跑会变，正文里会单独标出，不和论文里的 105 个产物混用。

## 1. 怎么读

两块问题不同。

- **用 vibe coding 做前端**：人提需求，模型写页面，用「页面能不能被用起来」验收。直接使用这个词的论文很多在研究人怎么用、安不安全。把前端能力测出数字的，主要是界面代码基准。它们常不自称 vibe coding，测的却是同一件事。
- **生成式可视化**：用模型把数据或分析需求变成图、多视图或仪表板。仪表板指同一页上的多张图加筛选，改一个条件，相关的图一起变。单独一张柱状图不叫仪表板。

前端这一块按任务难度分三档：截图还原、只给需求一次做成应用、多轮修改后还保持原来的功能。生成式可视化按现在的研究问题分四点：单张图的逐步生成、仪表板的中间表示、创作方式从聊天改成逐步或分叉、交互仪表板和多视图仍然差。

## 2. 用 vibe coding 做前端

### 2.1 这个词指什么

Andrej Karpathy 在 2025 年 2 月 2 日把 vibe coding 说成：用自然语言描述，接受模型写出的代码，不读 diff，报错就贴回去。他当时的例子是改侧边栏的内边距，对象是周末项目。原贴见 [archive.ph/yNSTA](https://archive.ph/yNSTA)。

后来这个词被用宽了。Simon Willison 的区分仍然有用：每一行都是模型写的，但人审过、测过、读懂了，那是把模型当打字员；不读代码、只看跑起来像不像，才是严格意义上的 vibe coding（[Ars Technica, 2025-03](https://arstechnica.com/ai/2025/03/is-vibe-coding-with-ai-gnarly-or-reckless-maybe-some-of-both/)）。

本文里的「做前端」按操作定义来收：自然语言或截图进去，模型写出可运行的界面，用跑起来的结果验收。不要求每篇论文都使用 vibe coding 这个词。

### 2.2 三档总表

| 档 | 输入 | 验收 | 目前到哪 | 代表工作 |
| --- | --- | --- | --- | --- |
| 截图还原 | 一张设计图 | 像不像、能不能编译 | 原生 HTML 已经比较高；React、Vue 低一档 | Design2Code，DesignBench |
| 一次做成应用 | 只有用户需求 | 浏览器把功能点完，是否全部通过 | 完整基准上大约一半 | ViBench，Vibe Code Bench，WebGen-Bench |
| 多轮仍保持原功能 | 连续多轮修改 | 后一轮之后，前面做对的功能还在不在 | 单轮可以到约 75%；连续五轮整段约 37% | EvoGenUI-Bench，FronTalk，MT-Web2Code |

### 2.3 第一档：按一张截图还原成页面

这一档问的是视觉还原，不是「只说需求、把应用做出来」。

#### Design2Code（NAACL 2025）

- 论文：Si 等，*Benchmarking Multimodal Code Generation for Automated Front-End Engineering*。
- 任务：给一张真实网页截图，生成能渲染成该页面的代码。
- 数据：人工挑选的 484 个真实网页。
- 结果：当时的前沿模型能做出结构完整的页面，但会漏掉区块，布局也不稳。GPT-4o 可以靠补充文字和看渲染结果再改来提升，并不是每个模型都能。论文把动态交互留成了后续工作。
- 限制：测的是静态页面像不像，不是点击之后功能对不对。

#### DesignBench（[arXiv:2506.06251](https://arxiv.org/html/2506.06251v2)）

- 作者：肖静瑜等，香港中文大学、新加坡管理大学。
- 任务：同一套生成、编辑、修复，覆盖原生 HTML/CSS、React、Vue、Angular。
- 规模：900 个样本。生成 430（React 109、Vue 118、Angular 83、原生 120），编辑 359（React 108、Vue 105、Angular 66、原生 80），修复 111（各框架约 27–28）。编辑数据来自 v0 上的 React 项目和 Vue0 上的 Vue 项目。
- 结果：
  - 框架代码难于原生 HTML。原生 HTML 的视觉相似度最高，编译基本能过；React 和 Vue 居中；Angular 最差。
  - Vue 的编译错误主要是模板没闭合、属性写错。React 是 JSX，Angular 是 TypeScript 组件结构。强模型在 Vue 上的编译错误已经很少，论文统计里 Claude 3.7 只剩 1 个 Vue 编译错误；弱模型仍然很多。
  - 抽出 30 个有编译错误的页面再交给模型修，各模型、各框架平均修对约一半（0.53）。
  - 模型几乎不用框架自己的组件化写法。论文报告的组件化实现比例大约是 React 0.24%、Vue 5%、Angular 19%。Vue 案例里，本该用 `v-for` 的重复列表被写成一段段写死的标签。
  - 编辑和修复的瓶颈是找不到该改的代码。只给代码比只给截图更有效；截图再加上代码，提升很小。
- 限制：修复样本每个框架只有二十多个。它没有测多轮对话里状态会不会丢。

#### 夹在第一档和第二档之间的工作

**Interaction2Code**（ASE 2025）把任务从静态截图改成「交互原型 → 代码」：127 个页面、374 个交互、15 类页面、31 类交互。失败集中在交互没做出来、视觉上不明显的交互，以及只给一张图时模型读不懂交互。

### 2.4 第二档：只给用户需求，一次做成能用的应用

这一档最接近 vibe coding 的定义：需求只写用户要做什么，不规定怎么实现，用浏览器把功能点完。

#### ViBench（CAIS 2026）

- 论文：Peter Zhong 等，*ViBench: A Benchmark on Vibe Coding*，ACM Conference on AI and Agentic Systems，2026，页 497–513。
- 出处：[DOI 10.1145/3786335.3813162](https://doi.org/10.1145/3786335.3813162)。没有 arXiv。PDF：[vibench.ai/assets/vibench-cais-2026-DZJHST1s.pdf](https://vibench.ai/assets/vibench-cais-2026-DZJHST1s.pdf)。代码：[github.com/ViBench/vibench-public](https://github.com/ViBench/vibench-public)。
- 任务：15 个来自生产痕迹的应用，105 个产物。包括从零做起，以及在已有实现上加功能。任务只写用户能看见的需求，不限制代码结构。
- 怎么打分：每个应用有自然语言测试计划。评估器是接在 OpenHands 上的另一个大模型。它先读生成出来的源码，再在一个一直开着的笔记本环境里一小段一小段地写 Playwright。每执行一段，拿回控制台输出、无障碍树和截图，再决定下一步点哪里。事先写死选择器不行，因为每次生成的标签和类名都会变。两个人对同一批步骤手工判断，自动评估和人在 1,082 个步骤上的一致率约 99%。
- 论文里的结果（OpenHands 标准环境，105 个产物）：

| 模型 | 一次全部做对 | 完全跑不起来 |
| --- | --- | --- |
| Opus 4.6 | 45.7%（48/105） | 2.9% |
| Opus 4.6 + Claude Code | 51.4%（54/105） | 0 |
| GPT-5.2 | 41.9%（44/105） | 10.5% |
| Kimi-K2.5 | 12.4%（13/105） | 9.5% |

- 开源模型没有一个明显高于这一档。DeepSeek-V3.2 完全失败率到 40%。在已有正确代码上加功能更容易；在模型自己写的代码上继续加，九个模型里有七个变差。
- 后来的小规模重跑：项目网站用 24 个从零做起的应用又跑了一轮，只覆盖从零做起。Opus 4.8 一次做对 87.8%，GPT-5.5 为 86.5%。这不是论文里的 105 个产物，不能直接比。见 [vibench.ai/results](https://vibench.ai/results)。
- 不要和另一篇 **VIBench** 搞混。那篇是 [arXiv:2605.28515](https://arxiv.org/abs/2605.28515)，测模型写代码时会不会偏爱自家技术栈。

#### Vibe Code Bench（[arXiv:2603.04601](https://arxiv.org/abs/2603.04601)）

- 任务：100 份应用说明（50 公开、50 保留），964 条浏览器流程，10,131 个子步骤。模型在沙箱里从零做出可部署应用，可以用浏览器、终端，以及登录、数据库、支付、邮件这类服务。
- 结果：16 个前沿模型里，最好的 GPT-5.3-Codex 通过了 61.8% 的流程。这是流程步骤的通过率，不是整个应用一次做对。开发时自己用浏览器测试，和最终成绩明显相关。
- 限制：技术栈只有 React/Vite 加 Supabase。论文写明结果不能外推到别的框架。

#### WebGen-Bench 与 WebGen-Agent

- **WebGen-Bench**（Lu 等，NeurIPS 2025，[arXiv:2505.03733](https://arxiv.org/html/2505.03733v2)）：101 个自然语言建站任务，647 条界面操作测试。用网页导航代理执行操作，核对页面反应。准确率按「通过 + 0.5 × 部分通过」计算。Bolt.diy 加 DeepSeek-R1 为 27.8%，加 Claude 3.5 为 26.4%（外观 3.0/5），加 GPT-4o 为 12.8%（外观 1.5/5）。
- **WebGen-Agent**（[arXiv:2509.22644](https://arxiv.org/html/2509.22644)，ICLR 2026）：在同一基准上加截图和界面操作反馈。Claude 3.5 从 26.4% 升到 51.9%，外观从 3.0 升到 3.9。DeepSeek-V3 为 52.6%，外观 3.8。报告中的最高是 Qwen3-Coder-480B，准确率 58.2%，外观 4.3。截图主要提外观，界面操作测试主要提功能。
- 读法：即使加上「看截图再改」，从零生成可交互网站的功能测试仍然大约一半。

### 2.5 第三档：连续多轮修改，还要保持原来的功能

#### EvoGenUI-Bench（[arXiv:2608.29387](https://arxiv.org/abs/2608.29387)）

- 作者：Peng 等，2026 年 8 月 29 日。
- 任务：150 个五轮任务，共 750 轮。三类场景：信息展示、可执行交互、接外部工具。
- 怎么打分：在浏览器里执行，留下截图、DOM、操作轨迹和运行日志。除了单轮通过和五轮整段通过，还有相邻轮保留率：上一轮做对的东西，这一轮还在不在。
- 结果：八个模型里最强的单轮通过 74.9%，五轮全部通过 37.3%。接到外部工具时，相邻两轮都还正确的比例降到 52.4%。展示类失败主要是信息结构；交互类失败主要是派生状态传不出去、可点击的东西没有绑上；接工具时还要再加上外部状态对不上。

#### FronTalk（ICML 2026，[arXiv:2601.04203](https://arxiv.org/html/2601.04203v2)）

- 任务：100 段来自真实网站的多轮对话。每一轮有一条文字指令，和一条表达同一意图的视觉指令（草图、截图批注）。
- 结果：后一轮覆盖前一轮已经做对的功能，遗忘率 4.3%–44.6%。用网页代理逐条核对历史指令（AceCoder）后，遗忘可以近乎消失。文字设定下通过率最高从 56.0% 到 65.3%；视觉设定下从 55.0% 到 60.2%。视觉批注比等价文字更难变成功能。
- Gemini-2.5-Pro 在多轮文字设定下通过率 75.0%、遗忘率 4.5%；视觉设定下通过率 68.7%、遗忘率 6.2%。这是单个强模型，不是所有模型的平均。

#### MT-Web2Code（[arXiv:2608.03474](https://arxiv.org/html/2608.03474)）

- 任务：102 个页面、16 个领域。两类编辑：补回整块缺失区域，以及只改一个小缺陷。
- 怎么造数据：从正确页面出发，依次注入结构或样式错误，再把修复顺序当成多轮任务。每一轮的目标状态是确定的。
- 结果：13 个编程代理都难以同时做到「改对目标」和「不动其余」。早期错误会滚进后面几轮。

### 2.6 还有几类相邻的失败，但不是上面的通过率

**Design Theater**（[arXiv:2607.22928](https://arxiv.org/html/2607.22928v2)）用 ChatGPT、Claude、Firebase Studio、v0、Bolt 生成 120 个界面。大约 25% 的设计理由没有落到界面上，功能类约 34%。提示里隐含的体验原则只认出大约一半；五个工具里有四个，把功能类原则真正做出来的比例不超过 6%。同一句提示，不同工具的布局会挤到一起。

无障碍方面，WWW / DIS / W4A 2025 的评测表明：基础对比度有时能过，语义结构过不了；把提示写成「请做无障碍」不能稳定变好。A11yn（[arXiv:2510.13914](https://arxiv.org/pdf/2510.13914)）用 WCAG 违规当奖励，在研究设置里把不可访问率降了约 60%。这是训练方法，不是现成产品的默认行为。

控制生成范围的系统工作也已经有了。UIST 2025 的 SQUIRE 用槽位中间表示，把修改锁在指定组件上，11 名前端开发者感到可控。CHI 2024 的 DynaVis 和 DirectGPT 是在预览里直接操作，再连到生成。这些锁的是通用控件，不是可视化的颜色尺度或联动。

### 2.7 点选是怎么做的

「浏览器自动点选」不是一篇论文的名字，是这些基准用来打分的方法。程序打开生成出来的页面，像用户一样点击、输入，再看页面变了没有。

有两种做法。

1. **写死的 Playwright 脚本。** 按按钮文字或选择器去点。页面结构固定时，一天内能跑通。vibe coding 每次生成的标签都不一样，脚本会断。
2. **代理循环。** ViBench 用的是这种。大模型读测试计划和源码，写一小段 Playwright，看截图和无障碍树，再写下一段。WebGen-Bench 则是让带视觉的网页导航模型看屏幕自己决定点哪里。后者更不依赖代码结构，也更容易点错、看错。

这里的代理不是另一个写前端的模型。写代码的模型负责把应用做出来；评估代理只负责打开页面、点击、判断这一步过不过。

可视化还有一层它们没做。柱状图若画在 Canvas 上，无障碍树里没有每根柱子，代理只能看见一块画布。颜色尺度有没有被筛选重算，要在点击之后读颜色、数据或 SVG 属性，不能只看「点完有没有反应」。

### 2.8 这一块的现状，以及还没回答的问题

- 单轮、静态、看起来像：研究里已经比较高，尤其是原生 HTML。
- 一次把整个应用按用户需求做对：完整基准上最好的闭源模型大约一半。更小、更新的从零任务集可以到八成以上，不能和 105 个产物的结果比。
- 连着改五轮并保持每一轮仍然正确：大约三分之一。
- 开源模型在端到端应用上仍明显更低。
- 还没有测的是：功能测试通过时，可视化编码是否仍然正确。例如筛选之后颜色按局部范围重涂，点击都在，图是错的。

## 3. 生成式可视化

这一块的前沿已经离开「一句话出一张图」。现在的工作把生成收进可检查、可局部修改的中间结果里。直接让模型写前端代码，仍然会改错不该动的地方。

### 3.1 第一点：单张图已经能拆成可查看、可修改的步骤

#### DeepVIS（VIS 2025，[arXiv:2508.01700](https://arxiv.org/pdf/2508.01700)）

- 问题：自然语言到图表通常是黑箱。人看不到模型为什么选这种图、这个编码，也难以只改错的那一步。
- 做法：把出图拆成逐步推理，并做了带推理步骤的数据 nvBench-CoT。界面上人可以看每一步，指出哪一步错，只改那一步。
- 结果：在基准上，带推理步骤的训练提高了出图质量；用例和用户研究表明，人能利用这些步骤改错。
- 限制：对象是单张图的规格推理，不是多视图仪表板在多轮对话里保住尺度和联动。

#### NVAGENT（ACL 2025）

- 问题：一句话出图在跨多张表时容易失败。例如「各职级教师指导了多少学生」要先把两张表对上。
- 做法：三个代理。一个处理数据库并筛上下文，一个规划图怎么画，一个把计划翻成代码并校验输出。
- 结果：在 VisEval 上比先前方法单表高 7.88%、多表高 9.23%。
- 限制：验收的是出图任务是否完成，不是后续修改会不会把已经正确的编码改坏。

### 3.2 第二点：仪表板仍是难点，直接写页面容易改串

#### NL2Dashboard（[arXiv:2601.06126](https://arxiv.org/html/2601.06126)）

- 判断：模型适合做分析，不适合直接写复杂页面。
- 做法：先生成一份轻量的中间表示，再渲染成仪表板。分析和页面实现分开。
- 对照：DashChat 这类端到端对话生成仪表板的系统，改一处时常把没要求改的部分一起改掉，而且很费 token。
- 意义：这和前端第三档的失败是同一种。差别是，这里被改坏的是仪表板上的图和布局，不只是按钮功能。

#### Data-to-Dashboard（[arXiv:2505.23695](https://arxiv.org/pdf/2505.23695)）

- 做法：多个代理从原始数据识别领域、抽概念、从多个角度产生洞察，再选图，组成仪表板。选图时用树状推理，比较几种图表方案。
- 评价：和单次提示的 GPT-4o 比，洞察是否贴领域、分析是否更深。主要是人和模型评分，不是浏览器把交互点完。
- 限制：三个数据集。它回答的是「洞察像不像分析师会说的话」，不是「筛选之后颜色和联动还对不对」。

### 3.3 第三点：创作方式从一条聊天改成逐步推荐，或者分叉

#### VisAutocomplete（VIS 2026，[arXiv:2607.15608](https://arxiv.org/html/2607.15608v1)）

- 作者：Hyeon Jeon、Sungbok Shin、Niklas Elmqvist。
- 问题：专家能认出好图，但很难知道下一步该改哪个编码。直接对话把整张图一次生成，人插不进中间步骤。
- 做法：按常见做法推荐下一步，例如下一个编码、变换或样式。人可以接受、修改，或一次委托多步。为了不用每步都调用大模型，它把大模型的改写逻辑蒸馏成一个函数：输入当前图表状态和推荐的那一步，输出更新后的规格。
- 对照：LLM vibe coding、Excel、自动荐图系统 TaskVis。
- 结果：复杂图的可表达性上，逐步推荐好过直接 vibe coding；上手难度和直接对话差不多。
- 意义：这是生成式可视化里，明确把「LLM vibe coding」当成对照并在复杂图上超过它的工作。它超过的是「复杂图能不能被清楚地做出来」，不是多轮之后尺度还在不在。

#### VisCanvas（VIS 2026，[arXiv:2607.21886](https://arxiv.org/abs/2607.21886)）

- 作者：Yuki Ueno、Bretho Danzy、Zhuojun Jiang、Chris Bryan。
- 问题：探索分析不是一条直线。聊天记录难以分支、合并、回到早先的一张图。
- 做法：用节点。文字节点生成或修改图，图节点用来看和收藏，边上可以分支、填空白、合并。输出是 Vega-Lite 一类的规格，不是一整页随意的前端代码。
- 实验：20 人，对照线性聊天。
- 结果：探索更多样，认知负担和可用性与聊天差不多。
- 限制：测的是探索是否更开，不是生成代码的功能正确率，也不是颜色尺度在后续编辑中有没有被改坏。

### 3.4 第四点：交互仪表板和多视图的还原仍然差

#### Dashboard2Code（ACL 2026）

- 任务：模型先自己点、自己筛一个已有的交互仪表板，再写出能复现该仪表板的代码。不是只看一张静态截图。
- 数据：DashboardMimic，180 个人工核过的 Plotly+Dash 仪表板，三个难度，八类常见交互。
- 打分：代码语义，加上真的去点交互，看视觉和交互是否一致。和人的判断比较一致。
- 结果：复杂档上，最强的模型仍然吃力。开源和闭源差距明显。摘要没有给出一个总通过率，这里不补一个数字。
- 和前端截图还原的差别：模型必须自己操作仪表板，才能看到筛选之后的状态。只看首屏截图会漏掉这些交互。

#### VA-Bench / MV-Bench（VIS 2026）

- 作者：赵越、曾琼等。VIS 2026 程序里的题目是 *VA-Bench: Benchmarking Multimodal Large Language Models for Visual Analytics Interface Construction*。同作者预印本题目是 MV-Bench，[arXiv:2607.19910](https://arxiv.org/html/2607.19910v1)。下面的数字来自预印本。
- 任务：从视觉设计生成协调多视图界面。标准答案来自 Tableau 工作簿，因为它们写明了数据绑定、视觉映射和交互。单次生成，不是多轮对话。
- 规模：92 个基础界面，重组后 1,048 个实例。五个多模态模型。
- 结果：

| 指标 | 最好结果 |
| --- | --- |
| 视觉布局 | 75.45% |
| 数据绑定 | 21.71% |
| 交互完整性 | 11.68% |
| 综合分 | Kimi K2.5 为 30.9% |

- 其余模型的综合分：Qwen3.5 Plus 25.51%，Claude Sonnet 4.5 25.27%，GPT 5.4 25.25%，GLM 4.6V 5.92%。静态外观比数据绑定平均高约 59 个百分点，比交互高约 65 个百分点。
- 迭代修改能提高代码可运行率，拉不开数据绑定和交互。
- 读法：看起来像，和数据、交互真的对，是两件事。

### 3.5 和 vibe coding 直接相关的用户研究

Zeng 等，*Towards Effective Generation of Interactive Visualizations with Vibe Coding: An Empirical Study*，[arXiv:2608.29550](https://arxiv.org/html/2608.29550v1)，2026 年 8 月 30 日。北京理工大学。这是目前直接测「用 vibe coding 做交互式可视化」的用户研究。核对过的 IEEE VIS 2026 接收列表里没有这一篇。

- 方法：78 名有可视化基础的计算机学生（53 男、25 女），自选题目和数据，做一周。工具不统一，主要是 Codex、Claude Code、Cursor、Copilot。21 人几乎全靠模型，54 人用模型辅助自己的结构，3 人只用来排错。测的是事后自评和访谈，不是统一任务上的正确率。
- 能力：从零搭框架、静态图和基础交互（提示、图例开关）较稳。35.9% 的人明确提到快速搭起框架和图表。复杂交互和多视图联动明显变差。模型按视图分别写代码时，会丢掉 brush/link 的共享状态。开放回答里，交互逻辑混乱 25.6%，视图间状态不同步 12.8%，视觉映射不当 12.8%。
- 体验：43.6% 的人卡在语义对不齐和提示难写；37.2% 说再改提示会引入新偏差；25.6% 不得不在对话和预览之间来回切。
- 人并没有退出：59.0% 的人仍要手改 10%–30% 的代码，只有 28.2% 认为小改即可。常用策略是分步加功能（61.5%）和给样例数据（59.0%）；给参考图的只有 32.1%。改动面大就交给代理，改几个参数就手改（42.3% 按工作量，38.5% 按改动粒度，26.9% 按自己是否还读得懂）。
- 个案：P41 做纽约犯罪地图。年份从 2006–2024 筛到 2013–2014 后，颜色按这一小段的最大值重新涂，低值看起来和全局高值一样饱和。筛选按钮是好用的，图的含义是错的。P21 则是协作做对了的例子：模型先给了条形图，人改成比较两年，最后一起做成哑铃图。这是个别协作，不是稳定能力。
- 论文自己写明的限制：样本是学生；模型和工具没有控制；只覆盖初次搭建，没有后续维护。正文没有给出 Likert 均值，所以不能把「效率很高」写成一个效应量。
- 讨论里提出但没有做成系统的三件事：在预览里点选再改代码；把交互怎么传状态画出来以便调试；局部锁定，规定哪些编码和规则不许模型改。

### 3.6 为什么不能让画图的模型自己验收

EuroVis 2025 上，Pandey 和 Ottley 用 VLAT 和 CALVI 测 GPT-4、Claude、Gemini、Llama 读图。常规图还可以，Claude 在 VLAT 上约 67.9%。识别误导图最多约 30%。折线图约 76%–96%，气泡图约 18.6%–61.4%，异常检测约 25%–30%。Gemini 对大约 22.5% 的题选择不答，其余模型约 7%–8%。

EuroVis 2026 的 *How Do LLMs See Charts?* 继续比较人和模型的高层读图。

这些结果的用处是：画图的往往就是同一个模型。再问它「这张图对不对」，它很容易觉得没问题。颜色范围和选中数据应该用写死的规则查。例如颜色必须按全部年份的最大值来涂，筛选之后这个最大值不能变。规则说变了，就是错，不用再问模型。

### 3.7 相邻、但不是「生成一张图」的工作

这些工作说明可视化和大模型的结合不只有生成。写进生成式可视化的材料里时，应该和上面四点分开。

- **模型操作已有的可视化系统。** VIS 2025 最佳论文 NLI4VolVis 用多个智能体和可编辑的三维高斯泼溅，让人用自然语言探索和编辑体数据。ProactiveVA 让代理在分析界面上主动提议操作，人先看再批准。它们生成的是操作，不是从零写一个前端。
- **用可视化看模型。** VIS 2025 荣誉论文 ConceptViz 看大模型内部特征对应什么概念。EuroVis 2026 的 *When the Chain Breaks* 和 RETRACE 把推理在哪一步断了画出来。
- **通用界面的语义层。** 首尔大学 Park、Seo 等，*Bridging Gulfs in UI Generation through Semantic Guidance*，CHI 2026，[arXiv:2601.19171](https://arxiv.org/html/2601.19171v2)。它们在对话和生成界面之间加了四层设计语义：产品、设计系统、功能、组件。系统标出每条语义落在界面的哪里，以及语义之间有没有冲突。14 名从业者对照带提示增强的聊天，两边用同一个生成模型。主观评分里，「能想清楚设计」从 3.93 到 6.14，「过程透明」从 3.79 到 5.64（7 分量表）。论文没有证明生成结果在客观上更正确。那四层管的是按钮、风格和页面功能，不管颜色尺度会不会因为筛选而重算。

## 4. 两边怎么对上

| | 前端 vibe coding | 生成式可视化 |
| --- | --- | --- |
| 看起来像 | 截图还原已经比较成熟，原生 HTML 高于 React / Vue | 多视图外观最好约 75% |
| 一次能用 | 完整基准上大约 50% | 单张图较可用；仪表板和联动仍差，交互完整性约 12% |
| 改完还对 | 五轮整段约 37% | 没有同等的整段通过率。已知失败是共享状态丢失、颜色尺度被筛选重算 |

前端已经能测「一次能不能用」和「改完旧功能还在不在」。可视化还少测一种情况：筛选和联动点得动，但颜色尺度或两个视图的选中数据已经被改错。这种错，功能测试会判通过。检查也不适合再交给画图的模型自己做。

若要把两边接上，现有材料支持的问法是：沿用前端基准的浏览器点选，把通过条件从「点得动」改成「颜色范围和共享选中没有被改坏」。生成仍然由模型做。要测的是检查和约束，不是再做一套从零出图的系统。
